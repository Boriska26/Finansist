# Архитектура

## Границы текущего этапа

Этапы 1 и 2 приняты. Прежнее сложное планирование отозвано. Реализован новый узкий бюджет; владелец разрешил следующий этап перед покупками: очередь push ВБРР Онлайн с ручным подтверждением. Ручной учёт сохранён, покупки остаются будущим разделом. Демонстрационные записи не создаются.

## Слои и DI

- `Finansist.App`: MAUI Shell, нижние вкладки, формы, ресурсы тем, навигация/диалоги и Android SQLite-адаптер.
- `Finansist.Core`: модели финансов, точный разбор сумм, расчёт остатков, интерфейсы, SQL/миграции, MVVM через CommunityToolkit.Mvvm.
- `Finansist.Core.Tests`: xUnit и тестовый Linux-адаптер к системной SQLite. Тесты используют отдельные временные файлы и синтетические данные.

Зависимости: App → Core ← Tests. `MauiProgram` регистрирует один LocalStore одновременно как ILocalStore, IFinanceStore, IBudgetStore и IBankImportStore, чтобы у операций и настроек был общий gate. AppViewModel хранит состояние темы/инициализации. FinanceViewModel отвечает за счета и историю. Редакторы создаются transient, чтобы каждый открытый черновик получил собственный ID и состояние.

`IFinanceNavigation` отделяет модели представления от MAUI и предоставляет переходы и подтверждения. Code-behind связывает модель с экраном, загружает данные при показе, обрабатывает системный Back и прокручивает форму к ошибке. Страницы создаются после ресурсов Application; FinancePage.ViewModel присваивается до InitializeComponent, поскольку x:Reference-команды обращаются к ней при создании XAML.

## SQLite и миграции

Android использует публичный `Android.Database.Sqlite`; тесты — `libsqlite3.so.0` через небольшой адаптер только для Linux. Интерфейс соединения содержит Execute, Scalar и Query. Параметры передаются отдельно от SQL. Внешнего SQLite NuGet-пакета или собственного нативного SQLite в APK нет.

База `FileSystem.AppDataDirectory/finansist.db` находится в приватном каталоге Android. `PRAGMA user_version` хранит версию:

- 0 → 1: `app_settings(key, value)` для выбранной темы.
- 1 → 2: `accounts(id, name, opening_minor)` и `operations(id, kind, account_id, destination_id, amount_minor, occurred_on, category, note)`, индексы по дате и обеим сторонам операции.

- Версия схемы 3 сохранена для совместимости с установленными 0.3.0/0.3.1. Новая база содержит только таблицы этапа 2. Ранее созданная planning_state остаётся без чтения и изменения; функций планирования в приложении нет.

- 3 → 4: salary_budget(id, revision, payload) — отдельный JSON-агрегат нового бюджета. Старая planning_state не читается и не меняется.

Обновление до схемы 4 сохраняет настройки, счета и операции. Новые таблицы изначально пусты. Наименование счёта проверяется на непустоту и дубликат (OrdinalIgnoreCase, в том числе для кириллицы). Все счета — RUB; мультивалютности на этом этапе нет.

Каждое обращение открывает соединение, включает foreign keys и busy_timeout 5 секунд, начинает транзакцию, проверяет/обновляет схему и выполняет действие. Ошибка откатывает всю транзакцию. Версия выше поддерживаемой блокирует операции без сброса базы. Android Close/Dispose и курсоры освобождаются. Синхронное I/O выполняется в Task.Run; SemaphoreSlim сериализует доступ singleton-хранилища.

## Деньги и операции

Суммы хранятся в SQLite INTEGER и C# long, в копейках. Разбор ввода использует decimal и принимает запятую или точку, максимум два дробных знака, без скрытого округления. Ограничение отдельной суммы/начального остатка — 1 трлн рублей по модулю. Операция строго положительна; тип задаёт направление. Переполнение расчётов контролируется через checked.

Остаток счёта = начальный остаток + доходы − расходы − исходящие переводы + входящие переводы. Баланс отдельно не хранится. Отрицательные остатки разрешены, начальный остаток не является доходом. Запись перевода содержит обе стороны и одну сумму; отдельного частичного списания/зачисления не существует. Общий итог при переводе не меняется.

Сохранение/изменение операции и пересчёт снимка выполняются в одной транзакции. Ошибка валидации или записи сохраняет прежнюю запись. У каждой формы стабильный UUID; повторный Save обновляет ту же запись, а не добавляет дубль. Это защита локального повторного сохранения, а не готовый протокол синхронизации. Даты — локальные календарные даты ISO `yyyy-MM-dd`, без часового пояса; будущие даты пока запрещены.

У перевода получатель обязателен и отличается от отправителя; у дохода/расхода получателя нет. Это проверяют Core и SQL CHECK. Внешние ключи не позволяют удалить используемый счёт. Из UI удаление счёта/операции требует подтверждения; физическое удаление пока окончательное, отмена и синхронизация не реализованы. Названия до 60 символов, заметки до 300. Пустая категория сохраняется как «Прочее»; у перевода категория фиксирована.

## UI и ошибки

Нижние вкладки и закреплённые кнопки действий рассчитаны на управление одной рукой. История использует CollectionView. Начиная с 0.4.1 по умолчанию показывает последние 10, длинные отфильтрованные результаты подгружаются по 10. Для расчёта баланса пока загружается весь локальный журнал; SQL-пагинация и оптимизация для очень больших архивов отложены до появления такой необходимости.

Темы используют AppThemeBinding. Формы прокручиваются, учитывают безопасные области/клавиатуру; при ошибке прокручиваются к сообщению. Сохранение блокирует повторные команды; поля не очищаются при ошибке. Отмена несохранённой формы требует подтверждения. После сохранения/удаления возврат на экран финансов запускает обновление снимка. Во время изменения не разрешается параллельное сохранение/удаление/отмена.

Показываются понятные сообщения StorageException/FinanceValidationException без SQL, стека, путей и содержимого базы. Финансовые данные не логируются. Тема применяется только после успешного сохранения и переживает обновление APK.

## Простое распределение зарплаты, версия 0.3.2

Основной путь: «Пришла зарплата / аванс» → сохранение реального дохода → вопросы о расходах до следующего поступления → расчёт трёх сумм → подтверждение. Если пользователь закрыл форму, доход остаётся в журнале и доступен для распределения на вкладке «Бюджет». Для обычного дохода в редакторе есть явный переключатель предложения распределения.

### Модели и формулы

BudgetDocument хранит отдельный счёт подушки, BudgetBill (конкретное обязательство на дату), IncomeAllocation (однократное распределение одного реального дохода), ExpensePurpose (назначение расхода) и исходный набор ID операций. Денежные значения — long в копейках; расчёты checked. BudgetCalculator не зависит от Android.

Доступная сумма ограничена суммой дохода и свободными деньгами на всех счетах кроме подушки после ранее оставленных сумм. При уже потраченном доходе предложение явно сообщает об уменьшении доступной суммы.

Для доступной суммы A и ещё не обеспеченных обязательств R:
- необходимое = min(A, max(A / 2, R));
- новый взнос в подушку = min(A / 5, A − необходимое);
- на себя = A − необходимое − взнос;
- нехватка = max(0, R − A).

Деление целочисленное, остаточные копейки входят в «на себя». Дополнительного минимального лимита радостей нет по просьбе владельца. При нехватке сначала уменьшаются радости, затем новый взнос; деньги со счёта подушки не используются. Необеспеченные платежи получают резерв по ближайшим датам, а нехватка явно показывается. Сохранение такого плана требует подтверждения предупреждения.

### Защита от повторного учёта

Один incomeId распределяется один раз. Каждая порция резерва хранит уже оплаченную сумму на момент её выделения. Покрытие накапливается в порядке распределений: max(предыдущее покрытие, оплачено на момент выделения) + новая порция. Требуемое новое финансирование = max(0, полная сумма − max(текущее оплачено, покрытие)). Это учитывает и частичную оплату до первого распределения, и оплату сверх прежнего резерва. Уже оплаченный или обеспеченный платёж не резервируется снова. Каждая операция расхода имеет максимум одно назначение; при выборе конкретного обязательства учитывается его оплата, при выборе общего «Необходимое» расход уменьшает общий остаток этой части. Без назначения новые расходы с обычных счетов уменьшают «на себя». Общие повседневные расходы не расходуют резерв конкретной неоплаченной аренды: при исчерпании повседневной части уменьшаются радости, затем показывается нехватка. Отрицательная сумма радостей сохраняется в расчётах со знаком, чтобы следующее поступление не создавало повторный свободный остаток.

Доход, подтверждённый в распределении, нельзя удалить или изменить по сумме, счёту, дате и типу до отмены распределения. Смена назначения расхода и его сохранение атомарны. Удаление расхода удаляет назначение и возвращает неоплаченную сумму в расчёт. Отмена распределения не удаляет ни доход, ни реальные переводы/расходы.

### Подушка и остатки

Предложенный взнос не создаёт перевод. Пользователь переводит деньги в банке, затем записывает обычный перевод в журнале. Предзаполненная форма «Записать перевод в подушку» использует тот же журнал; допускает частичную сумму. Переводы на выбранный счёт после начала бюджета уменьшают суммарное «ещё перевести», каждый ID учитывается один раз. Ранее существовавшие переводы не засчитываются как новый взнос. Обратный перевод уменьшает фактическую подушку и не считается зарплатой или новым бюджетом радостей.

«Уже в подушке» равно реальному балансу её счёта. «На себя» ограничено остатком обычных счетов после резервов; отрицательный остаток показывается как ноль для траты и отдельное предупреждение о нехватке. Другие нераспределённые доходы и начальные остатки не автоматически превращаются в бюджет радостей.

### Периоды и повторение

Дата следующего дохода выбирается пользователем (по умолчанию через 14 дней), сумма будущего дохода не запрашивается. Автоматического календаря праздников и прогноза зарплаты нет. Горизонт одного распределения — до трёх месяцев.

Аренду/рассрочку можно пометить ежемесячными. Следующие строки предлагаются при новом распределении до выбранной даты с прежней суммой, которую пользователь подтверждает или меняет. День 31 в коротком месяце ограничивается последним днём, затем возвращается к исходному дню. Повторение можно выключить; завершённый платёж отметить как более не нуждающийся в резерве. Такая отметка не создаёт расход и не меняет банковский баланс. Недостающие старые платежи остаются видимыми.

### Согласованность и UI

SHA-256 входных данных (снимок бюджета и журнала, дата, период, счёт и черновик платежей) защищает подтверждение устаревшего предложения. Расчёт и подтверждение повторно проверяются внутри транзакции. Изменение поля формы скрывает старое предложение и требует пересчёта. Редактор платежей использует revision, предотвращая перезапись изменений другого экрана.

BudgetViewModel / BudgetEditorViewModel находятся в Core; XAML и навигация — в App. Финансовые расчёты отсутствуют в code-behind. Формы сохраняют ввод при ошибке, обрабатывают возврат, имеют закреплённые нижние действия и AppThemeBinding.

### Границы текущего решения

Одна подушка на отдельном счёте, одна валюта RUB, фиксированная отправная пропорция 50/20/30. Это общий бюджет нескольких карт, без проверки достаточности конкретной карты для каждого платежа. Остатки частей переносятся между поступлениями, а не обнуляются по календарю. Банковского подключения и автоматического перевода нет. Проценты кредитов, сценарии будущих зарплат и сложные цели прежнего этапа 3 не возвращаются.


## Порядок и сворачивание счетов, 0.3.3

AccountLayout хранит список ID и флаг Expanded в app_settings/account_layout (JSON). Схема SQLite остаётся 4. ReadSnapshot применяет сохранённый порядок, поэтому порядок согласован и в списках выбора счетов. Удалённые ID игнорируются, новые добавляются в конец; переименование не меняет пользовательский порядок. При первом открытии без настройки используется прежний порядок name/id, список свёрнут.

SaveAccountLayoutAsync проверяет точное соответствие списка текущим счетам, отсутствие повторов и записывает настройки в обычной транзакции LocalStore. При изменившемся наборе счетов сохранение отклоняется без частичного применения.

FinanceViewModel содержит Accounts, VisibleAccounts, IsAccountsExpanded и команды ToggleAccounts/MoveAccount. В свёрнутом виде VisibleAccounts содержит первый счёт, в раскрытом — все. Новый порядок и состояние применяются в UI после успешного сохранения. Ошибка сохраняет прежний вид и показывает сообщение.

FinancePage использует MAUI DragGestureRecognizer на ручке и DropGestureRecognizer на карточке. Code-behind передаёт ID и положение относительно середины карточки команде ViewModel; порядок и SQLite остаются в Core. Перетаскивание разрешено только в раскрытом списке и при отсутствии записи. Пакет перетаскивания содержит только локальный ID счёта. Финансовые операции и остатки не меняются.


### Исправление событий MAUI 10.0.110, версия 0.3.4

В локальной Android DLL SendDragStarting вызывает DragStarting с исходным View, SendDrop вызывает Drop с Parent распознавателя. Обработчики FinancePage 0.3.3 ошибочно проверяли тип отправителя как DragGestureRecognizer/DropGestureRecognizer. В 0.3.4 GestureView принимает VisualElement напрямую либо распознаватель с VisualElement в Parent; BindingContext и позиция берутся с найденного элемента. Это устраняет программную отмену захвата до нативного StartDragAndDrop и потерю события отпускания.


### Удаление обязательного платежа, версия 0.3.5

В BudgetBill добавлен необязательный флаг Archived (false для прежних JSON), версия SQLite остаётся 4. DeleteBillAsync проверяет revision и помечает выбранный платёж и все записи его SeriesId как Archived=true, Settled=true, Monthly=false. Операция выполняется сразу после подтверждения в одной транзакции, независимо от несохранённых полей других строк. Неиспользованный резерв освобождается существующим расчётом закрытых обязательств. Исторические ID, финансирование и реальные расходы сохраняются.

Редактор скрывает удалённые строки, не создаёт их повторно и не возвращает пустые шаблоны после удаления всех сохранённых платежей. При удалении нового черновика запись в SQLite не производится. Если удаляется предлагаемая новая строка существующей серии, удаляется вся соответствующая серия с отдельным подтверждением.

Для новых расходов удалённый платёж недоступен. Редактор старого расхода сохраняет прежнее назначение и показывает пометку «удалён», чтобы исправление примечания не переводило расход в категорию радостей. Хранилище разрешает сохранение существующей связи, но отклоняет новую связь с удалённым платежом.

Подписи формы указывают сумму одного взноса и дату его оплаты, а не общий остаток рассрочки или конец договора. Для аренды это платёж за месяц, для продуктов — оценка на период до следующего дохода.


## Этап 4 — импорт push ВБРР Онлайн (0.4.0)

### Получение и источник

Android-служба BankNotificationListener наследует NotificationListenerService. Манифест требует BIND_NOTIFICATION_LISTENER_SERVICE, экспортирует службу только с системным разрешением и объявляет intent-фильтр. Пользователь открывает системные настройки и самостоятельно разрешает доступ. READ_SMS, RECEIVE_SMS, Accessibility и прямое подключение к банку не используются.

BankNotificationAccess выбирает фактически установленное приложение по названию ВБРР/VBRR среди видимых launcher-приложений. Intent queries объявлены в манифесте; QUERY_ALL_PACKAGES не запрашивается. Package ID сохраняется после явного выбора. До извлечения текста служба проверяет пакет и флаг сбора. При отключённом сборе и для остальных приложений текст не обрабатывается.

EnabledSince обновляется при включении/смене источника. Новые posted-события и активные уведомления при OnListenerConnected проверяются относительно этой даты. Сводные групповые уведомления пропускаются. Текст выбирается из EXTRA_BIG_TEXT, EXTRA_TEXT либо EXTRA_TEXT_LINES; размер ограничен 7999 символами вместе с заголовком. Ошибки сбора не логируются; нейтральный индикатор сохраняется в Preferences и показывается в очереди. Гарантии непрерывной работы после force-stop, ограничения ОС или нехватки места нет.

### Парсер и финансовый журнал

VbrrPushParser — чистый Core-код. Поддерживает Пополнение/Popolnenie, Оплата/oplata, Списание/Spisanie, необязательное СБП/SBP, RUB/R/р/₽, точку/запятую и разделители тысяч. Сумма берётся только непосредственно после слова операции; Баланс/Balans не записывается в журнал и не заменяет остаток. Название торговой точки предлагается как примечание, категория остаётся «Прочее».

Поступление не считается зарплатой автоматически. Списание требует явного выбора типа в форме. Время внутри текста показывается отдельно, дата предлагается из локальной даты PostedAt и проверяется пользователем. Известные сообщения авторизации и неподходящие тексты не копируются в очередь. При нескольких операциях в одном несводном тексте сумма не угадывается: пользователь получает предупреждение и разбирает текст вручную. Регулярные выражения имеют тайм-аут 100 мс.

Полученная запись имеет свой UUID, исходный push и данные разбора, первый account ID из сохранённого порядка на момент получения (либо null, если счетов нет). Перестановка счетов не меняет ранее предложенный счёт в очереди. Если счёт удалён, форма предлагает текущий первый; выбор можно исправить. Raw-текст хранится только в приватной SQLite, скриншоты владельца не используются как фикстуры.

### SQLite-схема 5 и атомарность

Миграция 4 → 5 добавляет notification_imports(id, event_key UNIQUE, fingerprint, payload, status, operation_id, received_at), индексы по статусу и fingerprint. Настройки источника хранятся в app_settings/notification_import. Остальные данные, включая неактивную planning_state, не меняются.

EventKey — SHA-256 от package/key/postedAt/отпечатка текста: точная повторная доставка не создаёт новую запись даже после отклонения или подтверждения. Другой notification key, postedAt или изменённый текст сохраняются отдельно. Совпадение нормализованного текстового fingerprint помечается как возможный повтор, а не удаляется. Это позволяет не потерять две одинаковые по сумме реальные операции. Pending, confirmed и dismissed сохраняются после перезапуска.

ConfirmImportAsync в одной BEGIN IMMEDIATE транзакции проверяет pending, сохраняет ledger/budget через общий SaveBudgetOperationCore и меняет статус очереди. ID новой операции равен ID кандидата. Повторное подтверждение отклоняется, ошибка любого шага откатывает весь процесс. Подтверждение существующей записи меняет только связь/статус уведомления, не сумму, категорию или назначение реальной операции. Ссылки на операции в очереди не являются FK: удаление реальной операции не возвращает старый push в pending.

ImportMatcher предлагает совпадения по сумме, счёту и дате в пределах одного дня; для перевода учитывается исходящая либо входящая сторона. Совпадение всегда подтверждает пользователь. Можно явно создать отдельную запись после предупреждения. Вторая сторона перевода связывается с тем же ledger ID вместо создания дохода или расхода. Финансовые суммы перевода не меняют общий баланс и не расходуют бюджет радостей.

### MVVM и навигация

ImportInboxViewModel управляет источником/доступом и списком очереди. OperationEditorViewModel повторно используется для проверки, уточнения суммы/счёта/даты/типа, назначения расхода, поиска совпадений, подтверждения и отклонения. Состояния несохранённой формы остаются в памяти до закрытия; сам кандидат остаётся в SQLite. IImportNavigation и INotificationAccess отделяют Core от Android и MAUI. Начиная с 0.4.1 SettingsViewModel показывает счётчик pending во вкладке настроек, обновление также выполняется при Window.Resumed. Интерактивное включение «распределить доход» открывает бюджет только для новой подтверждённой записи дохода; связывание со старой операцией повторное распределение не запускает.

### Границы приёмки

Поддерживается один выбранный ВБРР-источник и известный формат операций в RUB. Полная история банковского приложения и SMS не читаются; автоматически объединять по одной лишь сумме нельзя. На Android необходимо проверить разрешение, доступность текста реального push, работу при закрытом окне и восстановление службы на S24 FE. Синтетические unit/integration-тесты не заменяют эту проверку.

Основа Android-интеграции: https://developer.android.com/reference/android/service/notification/NotificationListenerService и https://developer.android.com/training/package-visibility/declaring .


## Настройки уведомлений и фильтры истории, 0.4.1

Кнопка очереди уведомлений перенесена из FinancePage в SettingsPage. SettingsViewModel использует общий AppViewModel для темы/статуса хранилища и IBankImportStore/IImportNavigation для счётчика и открытия очереди. Обновление выполняется при показе настроек и возобновлении окна. Финансовый экран больше не читает очередь уведомлений.

FinanceViewModel разделяет черновые параметры фильтра и применённые. Режимы: последние 10, включительный диапазон DateOnly, всё время. Типы: все, доход, расход, перевод. Сначала фильтруются тип и дата, затем записи сортируются по убыванию даты (для равных дат сохраняется порядок снимка SQLite). В первом режиме берутся 10, в остальных результат подгружается по 10. Возврат с редактора и Window.Resumed сохраняют применённые критерии текущей singleton ViewModel; несохранённые значения не применяются автоматически. Настройки фильтра не записываются в SQLite: после нового запуска снова последние 10 всех типов. Фильтр не меняет счета, общий баланс, операции и расчёты бюджета. SQL-схема остаётся 5; журнал уже загружается для расчёта баланса, поэтому фильтрация выполняется в памяти.

## Исправление конфликтов жестов — 0.4.4

Удалены SwipeGestureRecognizer с корневого Grid, CollectionView журнала и ScrollView обзора. Они конкурировали с прокруткой и выбором точки. Навигационные свайпы ограничены заголовками; кнопки переключения остаются доступны. FinanceChart обрабатывает StartInteraction и DragInteraction, поэтому маркер следует за пальцем.

Android FinanceChartHandler создаёт наследника штатного PlatformTouchGraphicsView MAUI 10.0.110. После Down перехват временно запрещён до определения направления, чтобы ScrollView не забрал первый Move раньше графика. Направление определяется после системного ScaledTouchSlop: явно горизонтальное движение (|dx| > 1,25 × |dy|) блокирует перехват родителем до конца жеста; вертикальное и диагональное остаются ScrollView. При вертикальном движении график не отправляет DragInteraction. Up/Cancel и отключение handler снимают блокировку. Решение опирается на проверенный локальный код PlatformTouchGraphicsView: штатная реализация сама отправляет Start/Drag/Cancel, возвращая true из OnTouchEvent.

ChartTouchTracker — небольшой независимый от платформы помощник UI; тот же исходный файл подключён в тестовый проект. Проверяются порог, обе оси/направления, фиксация выбора направления и сброс для следующего касания. Эти тесты не заменяют проверку нативной прокрутки на устройстве. Бизнес-расчёты и SQLite не изменялись.


## Свайп от края и вход в очередь — 0.4.5

FinanceSwipeHost — Grid с Android LayoutHandler. Нативный LayoutViewGroup наблюдает DispatchTouchEvent до доставки дочерним элементам: начало только в средней полосе высотой 160 dp, ширина зоны 28 dp. На основном экране активен левый край, в обзоре — правый. Для захвата нужен жест внутрь экрана минимум 56 dp с преобладанием горизонтали 1,5:1; вертикаль, диагональ и движение наружу отключают кандидат до следующего Down. Жесты в центре доходят до графиков и прокрутки без изменений. После захвата дочернему элементу посылается Cancel, навигация выполняется только на Up; Cancel навигацию не запускает. Passive BoxView показывает край и не перехватывает ввод. На Android 10+ SystemGestureExclusionRects резервирует только указанную полосу активного края под приложение, остальная кромка остаётся системному «Назад». Выбор даты в графике и его handler не менялись. Чистая логика EdgeSwipeTracker тестируется из того же исходного файла.

ImportReviewViewModel — singleton для кнопки финансов и проверок при входе. Читает ImportSnapshot, показывает количество всех pending. Shell.Loaded и Window.Resumed вызывают CheckNew; обычный OnAppearing финансов только обновляет счётчик. Запрос автопроверки, пришедший во время обновления счётчика, обрабатывается после него. ImportNavigation допускает автоматическое открытие только с корневых страниц вкладок, без модальных окон; флаг opening и проверка CurrentPage защищают от двойного Push. Редакторы и уже открытая очередь не прерываются.

Состояние «показано» хранится отдельным множеством ID в app_settings/seen_imports, схема остаётся 5. Только успешная загрузка видимой очереди помечает конкретные прочитанные строки; новые строки, пришедшие после снимка, остаются новыми. Множество при записи очищается от уже обработанных ID. Фоновые обновления скрытой ImportInboxViewModel убраны, чтобы не помечать невидимые записи. «Позже» закрывает очередь, не подтверждая и не отклоняя записи. Повторный вход не открывает её из-за старых отложенных строк; новый ID снова вызывает автопереход. Подтверждение операций и финансы этим механизмом не изменяются. Кнопка в Footer истории доступна для всех pending, а настройки источника остаются в настройках.
